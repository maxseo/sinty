## What and why

`vision.look` reads a picture in the project and returns text, because a tool result cannot carry pixels back into the turn. Audio has the same gap: `fs.read` is UTF-8, so an mp3 in `_inbox` is not speech. `stt.transcribe` reads the file and returns the transcript.

## Design decisions

The call follows embeddings: the tool plugin asks the core, the core resolves `models.routes.stt` (or Settings → STT), and the openai-compat provider posts multipart audio. There is no fallback to `models.default`. A chat model does not implement that endpoint.

The file cap is 25 MB, the transcription endpoint's own cap. mp4 and webm are accepted so a short clip can be transcribed without a separate extract step. The plugin token budget counts about one token per kilobyte plus the transcript, because the speech API does not return chat tokens.

Plugin `tool-stt` is default-on. Policy is ask.

## Rejected alternatives

Sending the clip as a chat attachment. The main turn still would not hear a file that only lives on disk.

A local whisper binary. The harness already reaches speech models through the provider card.

Falling back to the default chat model. That request fails at `/audio/transcriptions` with a model id that cannot transcribe.

## Migration notes

Set `models.routes.stt` (Settings → Models, route `stt`) to an openai-compat speech model, for example `openai/whisper-1`. The host of that provider must already be allowed, the same as its chat calls.

Skill: `sinty skills add ./skills/stt-transcribe`.

## Known limitations

A file over 25 MB is refused. The tool does not pull a soundtrack out of a long video first. Anthropic and OpenAI Responses do not implement `transcribe`. An empty transcript is returned as empty text (silence), not as an error.

## How to test

```bash
pnpm --filter @sinty/plugin-tool-stt test
pnpm --filter @sinty/plugin-provider-openai-compat test
```

The core test `transcribe() posts multipart audio` boots openai-compat against a local server and checks the multipart body.
