# Re-embedding after an embedding model or width change

- Date: 2026-10-22
- Area: packages/core (memory.ts, memory-router.ts, config.ts, sinty.ts), packages/cli (memory reembed, doctor), docs
- Plan step: queue after step 7 (`/workspace/sinty-memory-plan.md` section 12: "реэмбеддинг при смене модели эмбеддингов")
- Commits: `feat(memory): track the embedding model per vector, sinty memory reembed`

## What and why

The builtin store kept vectors in `facts_vec` (sqlite-vec `vec0`, width fixed at creation) with nothing saying which
model made them. Two failure modes:

1. **Another model, same width** (e.g. `text-embedding-3-small` → another 1536-wide model, or a provider switch):
   recall compared the new model's query vector with the old model's vectors. The distances are meaningless, so
   vector hits were noise ranked into RRF next to real FTS hits, silently.
2. **Another width** (`memory.dimensions` changed with the model): `facts_vec` stayed `float[old]`, the router
   passed its own width check, and the `INSERT` into `vec0` threw, so **every memory write with an embedding failed**.

## Files touched

- `memory.ts`: table `facts_vec_meta (fact_id, model, dims, created_at)`; `MemoryStore` option `embedModel()`;
  `vecWidth` (read from the `facts_vec` CREATE statement), `vecReady`; `vectorStatus()`; `rebuildVectors()`;
  `adoptLegacy()`; `countMissingVectors()` / `missingVectors()` now also return stale facts; `vecIds()` filters by
  model and width with a larger `k`; `syncVec()` writes the metadata; `deleteId()` removes it.
- `memory-router.ts`: the store gets `embedModel` = `models.routes.embed` while an embedder exists;
  `reindexVectors()` handles stale vectors and the width rebuild (with a width probe first) and returns `stale` and
  `rebuilt`; `checkVectors()` journals `memory.degraded` once per process.
- `config.ts`: `memory.reembed: "manual" | "auto"` (optional, manual when unset).
- `sinty.ts`: `memory.reembed: auto` runs `reindexVectors` in the background after start; `stop()` aborts it.
- `cli/bin.ts`: `sinty memory reembed` (`reindex` stays as the old name), output names stale and rebuilt; `doctor`
  prints the vector status (`warn` for stale vectors or a width mismatch, without failing doctor).
- Tests: `src/__tests__/reembed.test.ts` (5), `memory-router.test.ts` (new result fields).
- Docs: `docs/spec/memory.md`.

## Design decisions

- **Model id = the embed route string.** The route (`provider/model`) is what the user configures. A renamed
  provider id with the same model counts as a change: conservative, costs one re-embed.
- **Search skips stale vectors, FTS still finds the facts.** No mixed-space distances. `k` grows by the number of
  stale rows (capped at sqlite-vec's 4096) so current vectors are not crowded out by stale neighbours.
- **Legacy vectors are adopted once.** Before this change nobody could have changed the model without editing
  config.yaml, and Max's databases were all built by one route, so the first route the store sees is credited.
  Recorded in `memory_meta` so a later route change is detected.
- **Width mismatch: vectors off, writes keep working.** The rebuild drops vectors, so it only happens in the command
  (or `reembed: auto`), after a probe confirms the embed route really returns `memory.dimensions`.
- **Background job is opt-in.** Re-embedding spends tokens on the user's key; `manual` is the default, doctor and a
  one-time `memory.degraded` say what to run.

## Rejected alternatives

- A `model` metadata column inside `vec0` (sqlite-vec ≥ 0.1.6 filters on it in KNN): needs recreating `facts_vec`
  for every existing database, i.e. a re-embed just to migrate.
- Re-embedding automatically on start by default: spends money silently after a config edit.

## Migration notes

- Opening an existing `memory.db` creates `facts_vec_meta` and, when an embed route is set, credits all existing
  vectors to it. Nothing is re-embedded and nothing changes in recall for an unchanged config.
- A database whose `facts_vec` width differs from `memory.dimensions` stops failing writes and recalls with FTS only
  until `sinty memory reembed`.

## Known limitations

- Changing only the embedding provider's base URL (same route string) is not detected.
- With many stale vectors (> 4046) the KNN window is capped at 4096 and a few current neighbours can be missed until
  the re-embed finishes.

## How to test

- `node --test dist/__tests__/reembed.test.js` in packages/core; full suite as usual.
- `sinty memory reembed --dry-run` shows how many facts need a vector and how many are stale.
