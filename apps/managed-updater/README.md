# Managed updater — STAGED Windows managed-Node slice

No current installation/home has been switched. No service, task, shortcut, DNS, production credential or server deployment was created. Existing checkout is never an update target.

## Working/tested contract

Independent Node24 helper lives outside immutable application version folders. It uses its own private owner token over a Windows named pipe; no TCP update-control listener or arbitrary command endpoint. A signed release cannot specify command/args/scripts. Node executable is the running helper's executable; application entry is fixed `app/managed-main.mjs` exporting `startManaged({home,gate})` with health/stop lifecycle. New application code is authenticated by pinned Ed25519 signed release index and immutable SHA-256 artifact/version receipts, never TOFU/public-feed-supplied key.

Helper API on local pipe: GET /status; POST /catalog {index:base64,signature:base64}; PUT /artifacts/<sha> streaming; POST /review {version}; POST /apply {reviewId,confirm:true}; POST /recover. Every action requires separate owner-token Authorization. Browser UI cannot call this pipe directly. Signed source origin/version/platform/arch/channel, anti-replay sequence, prior immutable hashes and installed-version monotonicity are checked. `mode:development` rejects updates. Only stable/no-migrations/current dataSchema supported.

Versions are extracted into fresh staging, verified, atomically renamed into version+hash directories and integrity-receipted. Current selection is a separate flushed atomic JSON pointer, not a junction replacing running Windows files. The helper does not replace itself. Old versions remain. No arbitrary pre/post-update scripts.

Runtime-host owns instance gate: drain blocks new tracked calls and waits boundedly for existing calls. Busy timeout resumes the SAME prior process, not a duplicate. Old runtime is stopped through nonce-authenticated private control after identity check, never broad process-name/node/browser termination. The actual Sinty adapter tracks admitted mutating HTTP requests (including requests still reading bodies), active agent turns, memory work, plugin RPC and reembedding. Supervisor and executable background/channel/schedule/event/memory/context/server plugins fail closed; only static UI or explicitly rpc-only executable plugins are supported for this slice. rpc-only is a reviewed lifecycle contract, not sandbox detection of arbitrary background activity.

After graceful stop, scoped config/policy/AGENTS and actual SQLite online snapshots of journal/accounts are backed up. Secrets/key files, blobs and unrelated plugins are not copied/deleted/logged. Plugin DATA/config fingerprints and SQLite schema/user_version gate rollback. Row changes with unchanged SQLite schema are retained; DATA/config or schema changes block automatic downgrade, retaining both packages and modified data. There is no automatic database restore/wipe. DATA is fingerprinted, not backed up/restored by this prototype.

Journal writes and artifact files use file flush+atomic rename; records/receipts and abandoned operation locks are authenticated with installation secret. Dead, authenticated owned locks can be quarantined; live/unknown locks are not stolen. Real updater-process-death tests cover prepared/stop-intent/old-stopped/launch-intent/healthy/pointer-written/committed states. An uncertain spawn gap without ownership proof deliberately stays BLOCKED rather than risk a duplicate process; owner review dialog exposes blocked state and an authenticated safe-recovery action while core HTTP remains reachable; an independent recovery UI for a non-starting core remains pending. No OS power-loss/NTFS directory-fsync guarantee is claimed.

## Formats and building

`release.json`: strict version, platform win32/linux, arch x64/arm64, channel stable, independent coreVersion/sdkVersion, updaterProtocol:1, nodeRange, dataSchema, dataCompatibility:unchanged, migrations:none, changelog:CHANGELOG.md. Optional core/SDK ranges remain descriptive compatibility metadata; no migration scripts. Payload path is fixed app/managed-main.mjs. `scripts/harness-package.mjs --dir PREBUILT_RELEASE --out FILE.tgz` packages regular-file USTAR deterministically, no links/private keys/env files. Node24 is required externally; updating/bundling the Node runtime is not implemented.

Build: `node apps/managed-updater/build.mjs`. Output is standalone dist/src + vendor contracts; no root/core dist dependency. Tests: `node --test --test-concurrency=1 apps/managed-updater/src/manager.test.mjs` after build.

Bootstrap CLI is STAGED ONLY, NOT EXECUTED: dist/src/bootstrap.mjs requires explicit --root, --home, --public-key-file, --origin and --confirm-new-managed-root. The ordinary CLI refuses nonempty install root AND nonempty home and starts nothing. A separate in-process bootstrapStoppedHome capability prototype can transfer the SAME populated test home only after its owned managed runtime has authenticated, drained and stopped, SQLite has been snapshotted and fingerprints still match; forged/reused/changed-state proof is rejected. This is NOT legacy0.5.1 adoption. A safe first handover from existing0.5.1 using the SAME home, current owned launcher and closed DBs is NOT implemented; do not point it at the owner's home or suggest starting with a fresh home as a migration. Core-owned path protection includes managed helper root and home ownership lease. Windows bootstrap now creates a fresh protected owner+SYSTEM DACL root and helper construction verifies owner, DACL, control files, reparse points and replace-capable ancestor permissions. Existing roots are never silently re-ACLed. This is a bootstrap primitive, NOT a complete signed Windows installer/shortcut/service.

## Legacy bootstrap checkpoint (pt308u): narrow actual legacy boundary

`node apps/managed-updater/dist/src/legacy-plan.mjs --home HOME --install-root LEGACY_INSTALL` is READ ONLY. It reports unowned-running adoption unsupported, an existing ownership lock and managed lease; it accepts no execute/force/PID option and never stops a process. No such command was run against the owner home.

Internal staged API: `launchLegacyForAdoption({home,installRoot,expectedCoreHash,confirmOwnedLaunch:true})` starts only a fixed adapter loading pinned local0.5.1 core. It refuses providers, supervisor, enabled plugins, search paths or non-disabled defaults BEFORE executing plugins; starts legacy with background:false; exposes only three read-only loopback API paths. This constrained probe is not normal production runtime and cannot attach to an already-running unowned process. `stopLegacyForAdoption(session)` requires the actual spawned ChildProcess IPC/exit handle, not a caller PID. Concurrent cooperating launches share an exclusive home lock. Uncertain start/exit retains the lock and never guesses/kills a PID.

`adoptStoppedLegacy(root,options,proof)` requires an unforgeable one-use process-local stopped proof, same-home fingerprint and retained lock. Actual SQLite online backups run under fresh private snapshot-root ACLs; fingerprints compare logical SQLite rows/schema rather than ephemeral WAL/SHM bytes. Config/policy/AGENTS are scoped backups; secret files are neither copied nor logged. Changed DATA/config/DB state fails closed. Existing home plugin SDK junctions are preserved without following/copying them; core-owned path/ancestor reparse points, traversal/ADS/network roots are refused. Config/user data are not reset or restored over new state.

The real test loads unchanged packages/core/dist0.5.1 in a separate child with a populated synthetic home (actual accounts, chat/project, plugin DATA and SDK junction), verifies the legacy web API, stops only that owned child, adopts the SAME home, then starts a signed actual managed Sinty1004 test build and checks application build identity and retained records. This is distinct from the prior managed-to-managed handover; it does not prove migration of the owner current live installation or all production bundled plugins.

Windows tests perform an actual owner write under the protected DACL, inspect native ACLs, reject an intentionally unsafe Everyone-write dummy root/parent and junction/ADS/traversal cases. They do NOT impersonate a second Windows login. This machine shared Temp grants extra principals write access, so strict bootstrap correctly rejects that placement; disposable roots are tested below the already-private phase backup parent. No existing directory/home ACL was changed. Root/control checks trust the owner, SYSTEM and privileged administrators; no claim of protection against the owner/admin or OS power-loss is made.

Independent recovery (STAGED commands, not run on owner install): `node apps/managed-updater/dist/src/recovery-cli.mjs status ROOT` and `... recover ROOT --confirm`. These use the same authenticated journal/lock/owned-runtime safeguards without the web core. No force-delete, arbitrary command, PID override or automatic corrupt-journal discard. Unknown legacy locks and lost process-local adoption proof remain blocked for manual ownership investigation; resumable crash-journal legacy adoption/installer consent UI is still pending.

Current live PID/home, checkout/dist, SDK junction, Browser and git index remain untouched. No publisher key, production deploy/DNS/release or user migration was performed. Linux Docker adapter, restart-required plugin queue and sent-history thumbnails remain separate pending work.
