# Sinty Distribution Center — staged, not deployed

Separate Node 24+ process/workspace package. No runtime dependencies, no SintyHub database/authentication, no Docker socket, no harness home access. Target chosen by owner: **https://plugins.syntoffice.ru on Ingrid**. No DNS/server change has been performed.

## Implemented vertical slice

- `/admin`: harness light/dark design tokens, plugin/harness tabs, login/bootstrap, `.tgz` upload → draft, explicit publish confirmation with changelog/metadata, per-version hide/show, plugin-wide discovery visibility, last100 audit events.
- First owner requires explicitly configured separate bootstrap secret (>=32 chars). SQLite singleton transaction permanently closes initial creation after one admin. No public first-visitor ownership. Password scrypt; independent 8h HttpOnly SameSite=Strict sessions, Secure on HTTPS, CSRF and origin checks, bounded login attempts. Never store auth in browser localStorage.
- Uploads are immutable by kind/name/version/platform/architecture/channel; same bytes retry is idempotent, changed bytes409. Drafts are inaccessible to public artifact requests. Publication rechecks SHA-256. Artifact files are flushed and renamed before SQLite transaction commits. SQLite WAL/FULL; filesystem directory/NTFS power-loss durability is NOT guaranteed. Interrupted unreferenced temporary/orphan files are not published or silently deleted.
- Public unsigned-transport access requires no install credentials: `/index.json` + binary `/index.json.sig`, `/harness-index.json` + `.sig`, `/artifacts/<sha256>.tgz`. Indexes are Ed25519 signed with explicitly configured key OUTSIDE the data/artifact volume. Production transport HTTPS, origin fixed; harness clients must already trust its public anchor, never auto-import one from a feed.
- Plugin feed uses existing `sinty.plugins/1`, real PluginCatalogClient and transactional core. Hide affects discovery only, including future versions while plugin-wide hidden; already published hash URLs remain for rollback. No remote uninstall/disable.
- Harness feed `sinty.harness/1` records version/platform/arch/stable channel, changelog/core+SDK compatibility, hashes and data compatibility marker. `applySupported:false` explicitly means no harness application/bootstrap updater yet.

## Build/test (from checkout root, no live dist writes)

```
node node_modules/typescript/bin/tsc -p packages/core/tsconfig.json --outDir packages/core/.distribution-core-checkpoint
node node_modules/typescript/bin/tsc -p apps/distribution-center/tsconfig.json --noEmit
node apps/distribution-center/build.mjs
node --test --test-concurrency=1 apps/distribution-center/src/center.test.ts
```

The package `test` script performs prerequisite isolated core compile + center build. Build vendors only the standalone archive/release contracts into its own `dist/vendor`, no runtime links to a running harness. Tests use disposable keys/passwords, local HTTP fixtures and real synthetic plugin child processes; they make no model/site/browser calls. UI handlers have a DOM-fixture + real HTTP integration test, NOT a visual/browser acceptance test.

## Deferred production start (do not run before deployment preparation)

Built entry: `node apps/distribution-center/dist/src/main.js`. Required configuration:

- `CENTER_PUBLIC_ORIGIN=https://plugins.syntoffice.ru/`
- `CENTER_DATA_DIR`: dedicated persistent metadata/artifact volume; never a Sinty home/Hub volume
- `CENTER_SIGNING_KEY_FILE`: explicitly provisioned Ed25519 private PEM, read-only, outside data and image/public files
- `CENTER_BOOTSTRAP_SECRET_FILE`: separate read-only >=32-character initial-owner secret file; remove this configuration after setup. Absent secret leaves setup closed. No production secret/key is generated by this code or tests.
- `HOST` defaults127.0.0.1; `PORT` defaults3198. Containers use non-root node, internal0.0.0.0; reverse proxy terminates TLS. Never expose private bootstrap/key files in an artifact/image layer.

Optional container recipe builds from **already-built app dist only**, not the whole checkout: `docker build -f apps/distribution-center/Dockerfile apps/distribution-center/dist`. Recipe is not executed. Pin reviewed Node24 image digest, provision dedicated writable volume/readonly secrets and reverse-proxy/TLS before production. No automatic service/autostart configuration was created.

Backups: SQLite online backup API, or stop this center process cleanly and snapshot its dedicated metadata+artifact directory; do not casually copy a running SQLite file without WAL. Restore matching metadata/artifacts and the same signing identity from protected separate storage. Never copy a full harness home.

## Package input

Plugins: existing `scripts/plugin-publish.mjs` produces accepted USTAR `.tgz`; explicit files and explicit signing key path (no key inside package). Upload **only its .tgz**, not its local private key. Client verifies signature/hash/full manifest/core+SDK compatibility/permission delta before installation; center additionally enforces archive safety and structural release metadata, not the entire runtime manifest schema.

Harness draft test format: regular-file USTAR `harness/release.json`, optional referenced changelog and payload files. release.json requires strict `version`, `platform:win32|linux`, `arch:x64|arm64`, stable channel, independent `coreVersion`,`sdkVersion`, optional compatibility `{core,sdk}` ranges and `dataCompatibility:requires-review|unchanged|backward-compatible|forward-only` (informational, does not authorize migrations/rollback).

Plugin bounds remain20MB compressed/256MiB expanded/20k entries. Harness streaming bounds are512MiB compressed by default (CENTER_MAX_HARNESS_ARTIFACT_BYTES, at most2GiB),2GiB expanded/100k entries; no symlinks/hardlinks/PAX/devices/traversal/ADS/collisions, no env/key material. This bounded harness upload is a metadata/distribution foundation, NOT yet a full-size Windows installer channel: large-artifact streaming/format and platform adapters must be implemented before real managed harness release. No arbitrary public upload endpoint.
